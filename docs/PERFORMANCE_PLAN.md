# План производительных испытаний

## Метрика

`RTF = processing_seconds / audio_duration_seconds`.

RTF меньше 1 означает обработку быстрее длительности записи. Для пакетного режима важны также throughput, очередь и пиковая память, а не только средний RTF.

## Перед тестом

Зафиксировать commit приложения, модель/revision/hash, Python и зависимости, ОС, CPU/число ядер, RAM, GPU/VRAM/драйвер, тип диска, формат/частоту/каналы и состав искусственного набора. Исключить реальные звонки.

## Сценарии

1. Один файл после прогрева и без прогрева.
2. 10 файлов последовательно.
3. 10 файлов при параллельности 2.
4. 10 файлов при параллельности 4.
5. Параллельность 8 только если память и предыдущие результаты это оправдывают.
6. 100 задач через ограниченную очередь; не 100 копий модели.

Для каждого режима записывать общую длительность, wall time, средний/медианный/P95 RTF, пиковый RSS, CPU, GPU/VRAM, ошибки и рекомендуемую параллельность. Отдельно измерять время загрузки модели.

## Два разных требования

- **100 файлов в очереди:** достаточно ограниченного числа воркеров, если суточное окно обработки выдерживается.
- **100 одновременных живых звонков:** отдельная capacity-модель по streaming RPS/SPS, задержке, памяти и отказоустойчивости. В MVP не реализуется.

## Критерий рекомендации

Рекомендуемая параллельность — максимальная стабильно проверенная величина без OOM/ошибок, при которой throughput заметно растёт и P95 RTF соответствует согласованной задержке. Пока допустимая задержка неизвестна, итог может быть только измерением, не sizing-рекомендацией.
