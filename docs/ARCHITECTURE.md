# Архитектура

## Целевой поток MVP

```text
Хранилище звонков
  -> обнаружение завершённых файлов
  -> надёжная локальная очередь
  -> один или несколько ограниченных ASR-воркеров
  -> папка звонка: аудио + JSON + Markdown
  -> reference-файловый/loopback HTTP-контракт CRM
```

Путь одного файла реализован: watcher -> проверка стабильности -> папка звонка -> локальный адаптер T-one -> детерминированная постобработка -> атомарные JSON и Markdown. SQLite-очередь хранит канонический путь аудио и восстанавливает задачу после прерывания.

## Предполагаемые компоненты

- **CLI**: принимает `--input`, `--output` и локальный путь модели.
- **Валидация**: проверяет расширение, существование, безопасный `call_id`, читаемость аудио и наличие модели.
- **Аудио-адаптер**: декодирует WAV/MP3/FLAC/OGG через miniaudio, AAC ADTS через локальный PyAV, сводит в mono 8 кГц и не меняет источник.
- **ASR-адаптер**: скрывает API движка и запрещает удалённый идентификатор модели в runtime.
- **Постобработка**: без LLM добавляет базовую пунктуацию, применяет точные локальные замены и сохраняет raw ASR.
- **Сериализация**: формирует JSON `1.1` и читаемый Markdown, считает RTF, атомарно публикует оба результата.
- **Очередь**: SQLite/WAL хранит статус, наблюдённый размер/mtime, число попыток, время доступности и lease.
- **Воркер**: один процесс переиспользует один engine, атомарно забирает задачи и поддерживает lease heartbeat.
- **Архив звонков**: `data/calls/{call_id}/` хранит исходное аудио, машинный JSON и читаемый Markdown. Старые дополнительные артефакты хранятся в `legacy/`.
- **Reference CRM API**: loopback-only stdlib HTTP server атомарно публикует raw upload в `data/input`, читает безопасный срез статуса SQLite и возвращает готовый JSON. ASR и очередь не дублируются.

## Реализованное состояние очереди

```text
new --(размер/mtime стабильны)--> queued --(atomic claim)--> processing
  ^                                      |                     |
  |                                      | lease expired       +--> completed
  +------------ файл изменился ----------+                     |
                                                               +--> queued (bounded retry)
                                                               +--> failed
```

SQLite `BEGIN IMMEDIATE` и условный claim не позволяют двум процессам взять одну задачу. Heartbeat продлевает lease; после падения процесса истёкший lease при следующем старте возвращается в очередь до лимита попыток. Готовый корректный JSON переводит найденную задачу в `completed`, в том числе после сбоя между публикацией JSON и фиксацией статуса.

## Границы доверия

Аудио, локальные веса, процесс ASR и результаты находятся внутри корпоративного контура. Сеть не является необходимой частью runtime. Подготовка зависимостей и весов — отдельный контролируемый процесс с проверкой лицензий, версий и SHA-256.

## Подтверждённые требования

- обработка русской телефонной речи без внешних API;
- соответствие `call_id` имени результата;
- локальное хранение весов;
- неизменность исходного аудио;
- JSON-контракт и явные статусы;
- CRM-специфичная интеграция отложена; есть только нейтральный reference-контракт;
- T-one проверяется первым, whisper.cpp — только резерв.

## Временные предположения

- имя файла без расширения является `call_id`;
- один файл соответствует одному звонку;
- разработческий greedy runtime проверен на Python 3.11/Windows 10 и Python 3.12/macOS; промышленная ОС неизвестна;
- staging-каталог и архив звонков доступны локально или как корпоративный файловый ресурс с обычной семантикой файлов;
- один JSON публикуется атомарной заменой временного файла;
- сегменты T-one можно преобразовать к `start/end/text` без потери результата.

## Открытые вопросы

Основной список ведётся в `OPEN_QUESTIONS.md`: каналы, форматы, объёмы, задержка, ресурсы, требования к диаризации, таймкодам, хранению и доступу.

## Будущие возможности, не входящие в MVP

- масштабирование очереди по измеренному RTF;
- production ingress/callback/auth для CRM;
- разделение каналов или говорящих после отдельного согласования;
- контролируемое обновление модели с сохранением версии транскрипции.
