# Спецификация продукта

## Бизнес-проблема

Телефонные разговоры хранятся в корпоративной CRM как аудиофайлы, но их содержание нельзя быстро показывать как текст или передавать внутренним техническим потребителям. Передача аудио и транскрипций внешнему провайдеру недопустима.

## Цель пилота

Показать автономный локальный сервис, который после завершения записи принимает аудиофайл, извлекает безопасный `call_id`, распознаёт русскую речь заранее подготовленной локальной моделью и создаёт самодостаточную папку результата:

```text
data/input/1234.wav
  -> data/calls/1234/
       1234.wav
       1234.json
       1234.md
```

JSON предназначен для машинной интеграции, Markdown — для просмотра человеком. Исходное аудио не изменяется и не удаляется.

## Пользователи

- оператор или администратор локального сервиса;
- будущая команда CRM, читающая версионированный контракт;
- специалисты ИБ и эксплуатации, проверяющие поставку, автономность и журналы;
- владелец продукта, утверждающий требования качества и критичные типы ошибок.

## Вход

- завершённый локальный аудиофайл WAV, MP3, FLAC, OGG или AAC ADTS;
- русский язык;
- на пилоте `call_id` берётся из имени файла и соответствует `^[A-Za-z0-9][A-Za-z0-9_-]{0,127}$`;
- один `call_id` соответствует одной записи и не перезаписывается неявно.

Фактические CRM-кодеки, каналы, частоты, средняя/максимальная длительность и способ передачи ещё должны быть согласованы.

## Выход

### JSON

UTF-8 JSON по схеме `1.1` содержит:

- `call_id`, `status`, имя источника и язык;
- длительность, processing time и real-time factor;
- идентификатор локальной модели, версии исходного кода/весов и decoder;
- очищенный `text` и исходный `raw_text`;
- сегменты `start/end/text/asr_text`;
- метаданные детерминированной постобработки;
- время создания/завершения и структурированную ошибку.

### Markdown

Markdown хранится рядом с аудио и JSON и содержит ссылку на исходное аудио, метаданные модели, полный текст, фрагменты с таймкодами и предупреждение о ручной проверке критичных данных. Он содержит полную транскрипцию и защищается так же, как аудио и JSON.

## Границы пилота

В пилот входят:

1. Ручная CLI-обработка и фоновый worker каталога.
2. SQLite-очередь со стабильностью файла, уникальностью, lease, bounded retry и восстановлением.
3. Локальная загрузка заранее подготовленных моделей без автоматического runtime-download.
4. Основной Whisper large-v3/`whisper.cpp` quality-путь на Windows/NVIDIA и T-one/greedy CPU fallback.
5. Атомарные JSON и Markdown, неизменность исходного аудио.
6. Детерминированная постобработка с сохранением raw ASR.
7. Нейтральный файловый и loopback-only reference HTTP-контракт.

Production CRM ingress, auth/TLS, callback, хранение и политика ревизий определяются совместно с CRM- и инфраструктурной командами.

## Подтверждённое качество

На шести открытых файлах FLEURS `ru_ru/test` (CC-BY-4.0), 84,96 с и 135 слов подготовленного чтения:

- Whisper large-v3: micro WER `2,96%`, macro WER `2,22%`;
- T-one/greedy: micro WER `7,41%`, macro WER `6,57%`.

Выборка содержит три мужских и три женских голоса, но не является набором звонков: в ней нет телефонного диалога, телефонной полосы, шума и перебиваний. На отдельном искусственном тесте Whisper ошибочно превратил «четыре ноля и один» в `4001`, поэтому качество критичных реквизитов не считается принятым.

Подробная методика и ошибки: [QUALITY_EVALUATION.md](QUALITY_EVALUATION.md).

## Критерии успешной транскрибации

- входной файл сохранён без изменения;
- результат имеет схему `1.1` и тот же `call_id`;
- используются только заранее подготовленные локальные runtime и модель;
- JSON и Markdown опубликованы полностью и атомарно;
- длительность, processing time и RTF измерены;
- raw ASR не потерян при постобработке;
- логи не содержат текст записи;
- ошибка представлена безопасным структурированным статусом.

Это критерии корректности одной операции, а не критерии допуска качества или безопасности всей поставки.

## Acceptance gates пилота

До обработки корпоративных данных должны быть отдельно закрыты:

- **Windows acceptance:** чистая поставка, первый staging, повторный offline-запуск и контрольный end-to-end результат;
- **телефонное качество:** согласованный набор диалогов с каналом, шумом, скоростью и перебиваниями;
- **VAD:** неречевой regression уже даёт 0 слов на тишине/шуме/тоне; для допуска остаются критерии пропуска тихой телефонной речи и длинных пауз;
- **таймкоды:** размеченный набор и согласованный допуск границ сегментов;
- **критичные поля:** exact-match пороги для сумм, дат, имён, отрицаний и реквизитов;
- **security:** OS-level deny-all egress для фактических Python и нативного ASR-процессов, наблюдение DNS/соединений, hashes, SBOM/CVE/license review;
- **производительность:** sustained RTF, CPU/GPU/RAM и обоснованная параллельность на целевом оборудовании;
- **эксплуатация:** права, хранение, backup, аудит доступа и безопасное удаление.

Пройденный неречевой VAD regression не означает, что тихая телефонная речь и точность границ таймкодов уже приняты. Успешный локальный инференс сам по себе не закрывает security gate.

## Вне текущего проекта

Суммаризация, LLM-анализ и коррекция, эмоции, контроль сотрудников, биометрия и идентификация личности, сложный UI, обучение/дообучение, живая транскрибация и автоматическое принятие бизнес-решений. Эти функции не нужны для завершения текущего пилота.
